# fiatallocators on AMD GPUs: background and implementation note

This note is for whoever (person or agent) implements the AMD version of `fiatallocators`. Read
`README.md` first. Part 1 summarises the work that led here, part 2 what to implement, part 3 what
to ask before coding.

## 1. Background

### 1.1 The goal

FIAT's double stack (two LIFO stacks, lower and upper side, in one buffer) allocates its whole GPU
buffer up front, so its size must be known in advance. The idea is to do on GPU what the OS does on
CPU with virtual memory:
- reserve a large range of device virtual addresses (no memory);
- map physical memory into it on demand, as each side grows;
- never move an address: CUDA graphs, FFT plans and MPI registrations stay valid.

On NVIDIA this is the CUDA VMM driver API (`cuMemAddressReserve`, `cuMemCreate`, `cuMemMap`,
`cuMemSetAccess`). On AMD, HIP has the same API (`hipMemAddressReserve`, `hipMemCreate`, ...).

### 1.2 History (NVIDIA)

1. **A C/Fortran prototype** (`../doublestack`, not on GitHub), on A100 nodes (ECMWF ac). It
   showed on-demand mapping, stable addresses, OpenACC, CUDA graphs and cuFFT plans working on
   the arrays.
2. **The MPI problem.** An array of the stack can cross a chunk boundary, so it spans two physical
   allocations (two `cuMemCreate`). With CUDA-aware MPI between nodes:
   - UCX widens a registration to the allocation returned by `cuMemGetAddressRange`, which covers
     only the first allocation. The transfer fails with "local protection error" (UCX 1.21) or
     "Remote access error".
   - With the exact range, registration through `nvidia_peermem` (`ibv_reg_mr`) fails with
     "Bad address". This is the case on the A100 nodes: proprietary GPU kernel modules, no DMA-BUF,
     kernel 4.18.
   - A minimal verbs test, without MPI, isolates this:
     `../vmm-span-checks/vmm_verbs_check.c`.
3. **NVIDIA (Matt Bettencourt)** pointed to [openucx/ucx#12186](https://github.com/openucx/ucx/pull/12186)
   and suggested building our own stack.
4. **On the GH200 nodes (ECMWF ag)** it works. They have open kernel modules, kernel 5.14 and
   DMA-BUF, and we built UCX `v1.23.x` (which contains #12188, the backport of #12186):
   - `cuMemGetHandleForAddressRange` and `ibv_reg_dmabuf_mr` accept a range that straddles two
     allocations;
   - with UCX `v1.23.x` loaded through `LD_PRELOAD` under the HPC-X Open MPI, a straddling buffer
     goes at 68.4 GB/s, against 70.0 GB/s for one allocation;
   - with the UCX of HPC-X 2.25.1, it fails.
5. **Rejected and fallback workarounds.**
   - Splitting MPI messages at chunk boundaries works but was **rejected**: do not propose it.
   - `UCX_IB_GPU_DIRECT_RDMA=no` (staging through host memory) works everywhere, but on GH200 it is
     about 2.5 times slower.
6. **`stackdemo`** (github.com/pmarguinaud/stackdemo) is a small Fortran/OpenACC demonstrator of
   the principles: a host mirror declared once with `acc_map_data`, CUDA graphs replayed after the
   stack grows, and MPI on straddling arrays. Its `PORTING_AMD.md` covers the AMD questions for
   that demonstrator, many of which apply here too.
7. **`fiatallocators`** (this repository) is the full library. It has CPU and NVIDIA
   implementations, all tests pass on ag, and the MPI test passes on two nodes.

### 1.3 Design decisions (from `../implement.txt`, agreed with Philippe)

- **Interface.**
  - Abstract base class `ALLOCATOR_BASE`, and a factory `NEW_ALLOCATOR` that returns a
    `CLASS (ALLOCATOR_BASE), POINTER`.
  - `INIT (KSIZE [, LDDEBUG] [, LDVERBOSE])` and `DESTROY` (explicit; `FINAL` as a fallback).
  - `ALLOCATE (X, UBOUNDS [, LBOUNDS] [, KSIDE])` and `DEALLOCATE (X)`, for kinds JPIM, JPIB, JPRM,
    JPRD and JPLM, ranks 1 to 5, generated by fypp.
- **Allocators.** Three, each with a CPU and a GPU class:
  - double stack (VMM on GPU);
  - fixed buffer (two sides; prints the peak used);
  - peak (plain `ALLOCATE`; prints the peak).
- **Sides.** A current side (`SET_SIDE`/`NEXT_SIDE`), plus an optional `KSIDE` for one allocation.
  The side is found from the address at `DEALLOCATE`. LIFO is checked per side, except for peak.
- **Features.**
  - Kept: alignment and chunk size as module parameters; debug fill of freed memory; verbose mode;
    zero-size arrays; `ABOR1` (`ERROR STOP 1`, to be replaced by FIAT's).
  - Not wanted: "steal" policy, trim, environment variables, measurement mode, thread safety.
  - `DESTROY` with live arrays releases them, with a warning in verbose mode.
- **GPU arrays.** They are host pointers into a host mirror mapped once to the device range, so
  `PRESENT`, `UPDATE` and `HOST_DATA` work on them.
- **Vendor code.** NVIDIA and AMD share the GPU classes; only the helper functions differ.
  **On AMD the offload model is OpenMP** (not OpenACC).
- **Build.** CMake, nvfortran only so far. This must change for AMD (section 2.4).

## 2. What to implement

### 2.1 The helper module

The GPU classes (`doublestack_gpu_mod.F90`, `fixed_gpu_mod.F90`, `peak_gpu_mod.F90`) call only
`GPU_HELPERS_MOD`. The AMD version must provide the same public routines, with the same arguments.
Addresses are `INTEGER (KIND=C_INTPTR_T)`.

| Routine | NVIDIA (`gpu_helpers_nvidia.F90`) | AMD |
|---|---|---|
| `GPU_INIT` | `acc_init`, `cuCtxGetCurrent`, `cuCtxGetDevice` | `omp_get_default_device` (or the device set by the program), `hipSetDevice`/`hipGetDevice`; make sure the OpenMP runtime is initialised on that device |
| `GPU_MEMORY_SIZE ()` | `cuMemGetInfo_v2` | `hipMemGetInfo` |
| `GPU_VMM_GRANULARITY ()` | `cuMemGetAllocationGranularity` | `hipMemGetAllocationGranularity` |
| `GPU_VMM_RESERVE (KBYTES)` | `cuMemAddressReserve` | `hipMemAddressReserve` |
| `GPU_VMM_FREE (KDEV, KBYTES)` | `cuMemAddressFree` | `hipMemAddressFree` |
| `GPU_VMM_MAP (KDEV, KBYTES)` | `cuMemCreate` (`gpuDirectRDMACapable`), `cuMemMap`, `cuMemRelease`, `cuMemSetAccess` | `hipMemCreate`, `hipMemMap`, `hipMemRelease`, `hipMemSetAccess` |
| `GPU_VMM_UNMAP (KDEV, KBYTES)` | `cuCtxSynchronize`, `cuMemUnmap` | `hipDeviceSynchronize`, `hipMemUnmap` |
| `GPU_MALLOC (KBYTES)`, `GPU_FREE (KDEV)` | `acc_malloc`, `acc_free` | `omp_target_alloc`, `omp_target_free` |
| `GPU_MAP_DATA (KHOST, KDEV, KBYTES)` | `acc_map_data` | `omp_target_associate_ptr (host, dev, bytes, 0, device)` |
| `GPU_UNMAP_DATA (KHOST)` | `acc_unmap_data` | `omp_target_disassociate_ptr (host, device)` |
| `GPU_CREATE (KHOST, KBYTES)`, `GPU_DELETE` | `acc_create`, `acc_delete` | no single OpenMP call: `omp_target_alloc` + `omp_target_associate_ptr`, then disassociate + `omp_target_free`. The helper must remember the device address of each host address (an internal table), unless the interface is changed so that `GPU_CREATE` returns it. Propose one. |
| `GPU_MEMSET (KDEV, KBYTE, KBYTES)` | `cuMemsetD8_v2` + synchronisations | `hipMemsetD8` (or `hipMemset`) + `hipDeviceSynchronize` |

Points to check on the target system, against the ROCm headers (`hip/hip_runtime_api.h`):

- **VMM support.** `hipDeviceGetAttribute (hipDeviceAttributeVirtualMemoryManagementSupported)`
  must be 1; abort otherwise. Use a recent ROCm (6.x).
- **Structure layout.** The `BIND (C)` copies of `hipMemAllocationProp`, `hipMemLocation` and
  `hipMemAccessDesc` must match C exactly. Write a small C program printing `sizeof` and `offsetof`
  of each field, compare with `C_SIZEOF` in Fortran, and keep it as a test.
  - On NVIDIA, `allocFlags` is 8 bytes and `gpuDirectRDMACapable` is set by writing 256 into a
    64-bit integer. Check what HIP has.
- **Enum values.** Read the values of `hipMemAllocationTypePinned`, `hipMemLocationTypeDevice`
  and `hipMemAccessFlagsProtReadWrite` from the headers; do not copy the CUDA ones.
- **Symbol names.** HIP symbols are not versioned like `cuMemGetInfo_v2`; check them with
  `nm -D libamdhip64.so`.
- **OpenMP mapping.** Check that `omp_target_associate_ptr` accepts a large device range (up to
  the device memory size) of which only a part is mapped. The design relies on this, and it works
  with `acc_map_data` on NVIDIA. If it does not, report it: do not change the design without asking.
- **APUs.** On MI300A (shared memory), check how the compiler treats the mirror. Prefer explicit
  mapping, as on discrete GPUs.

### 2.2 How to select the vendor (choice to make)

Philippe asked to see both options, with their complexity, before choosing:

1. **Two modules with the same name**: `gpu_helpers_nvidia.F90` and `gpu_helpers_amd.F90`, one
   compiled according to the CMake option `GPU_VENDOR` (the current build already does this).
   Each file is plain, with no preprocessor. Any change to the interface must be made twice.
2. **One module with `#ifdef`**: shared declarations, and vendor blocks around each call.

Write the AMD module as option 1 first, since it is ready to plug in. Then show what option 2
would look like (for example two or three routines merged), and report the line counts and
duplications of each, so that Philippe can choose.

### 2.3 Tests

The tests use OpenACC directives (`UPDATE`, `PARALLEL LOOP PRESENT`, `HOST_DATA USE_DEVICE`,
`ASYNC`) and CUDA graphs (`tests/cuda_graph_mod.F90`). On AMD they need:

- **OpenMP target directives:**
  - `target update to/from`;
  - `target teams distribute parallel do` (the mirror makes the arrays present);
  - `target data use_device_addr`/`use_device_ptr`;
  - `nowait` + `depend` in place of `ASYNC`.
- **HIP graphs**: `hipStreamBeginCapture`, `hipStreamEndCapture`, `hipGraphInstantiate`,
  `hipGraphLaunch`. Check how to get the HIP stream used by `nowait` target regions (OpenMP
  interop: `omp_get_interop_ptr` with `omp_ipr_targetsync`). Check also that the compiler's kernels
  can be captured, first on a one-kernel case. Report a failure instead of replacing the kernels
  with hand-written HIP.
- **How to organise them.** Two copies of the GPU tests (OpenACC and OpenMP), or one source with
  the directives generated by fypp macros or `#ifdef`. Propose, and let Philippe choose.

The CPU tests have no directives in their CPU path and need no change.

### 2.4 Build

- **Compiler.** `CMakeLists.txt` currently rejects any compiler other than nvfortran. Allow the
  AMD compiler chosen (section 3).
- **Flags and libraries.**
  - `ACC_FLAGS` becomes OpenMP offload flags, for example `-fopenmp --offload-arch=gfx90a`
    (MI250X) or `gfx942` (MI300), depending on the compiler.
  - Link `-lamdhip64` in place of `libcuda`/`libcudart`.
- **fypp.** It is pure Python (`pip install fypp`).
- **Environment.** Add `scripts/env_<system>.sh` and `scripts/run_mpi_<system>.sh`, like the ag
  ones.

### 2.5 MPI on arrays that cross chunks

This is the open question on AMD. The steps:

1. **Registration without MPI.** Port the verbs test (`../vmm-span-checks/vmm_verbs_check.c`):
   register a range straddling two `hipMemCreate` allocations, with `ibv_reg_mr` and with DMA-BUF
   (`hipMemGetHandleForAddressRange`, if HIP has it, plus `ibv_reg_dmabuf_mr`). This applies to
   InfiniBand. On Slingshot (`cxi`), ask Philippe how to test registration without MPI.
2. **`test_mpi` with `fixed` and `peak`.** One allocation per array: this separates porting bugs
   from the registration question.
3. **`test_mpi` with `doublestack`.** If it fails, report the exact error and the versions:
   - Open MPI + UCX ROCm: check how UCX's `rocm_copy`/`rocm_ipc` find the allocation of a pointer;
     [openucx/ucx#12138](https://github.com/openucx/ucx/pull/12138) is a ROCm change to read first;
   - Cray MPICH: check how GPU memory is registered (`MPICH_GPU_SUPPORT_ENABLED=1`).

## 3. Ask Philippe before coding

1. **Target.** The system and GPU (MI250X, MI300A or MI300X), the ROCm version, the Slurm
   partition and account, and the network (Slingshot or InfiniBand).
2. **Compiler.** The Fortran compiler with OpenMP offload: HPE Cray CCE (`ftn`), AMD `amdflang`,
   or GCC.
3. **MPI.** Cray MPICH, or Open MPI + UCX (ROCm).
4. **Tests.** Two copies (OpenACC and OpenMP), or one source with generated directives
   (section 2.3).
5. **`GPU_CREATE`.** An internal table in the AMD helper, or a change of the interface
   (section 2.1).
6. **Vendor selection.** Two modules or `#ifdef` (section 2.2), once both are shown.

## 4. Working rules

- Run git as `/bin/git`. No AI attribution in commits. Commit or push only when asked.
- Keep the NVIDIA version building and passing. Do not modify files other than those needed for
  AMD without asking.
- Keep test tooling minimal; no side investigations without asking.
- Put `timeout` in front of every `mpirun`/`srun`: failed registrations can make MPI hang.
- Give binaries and outputs job-specific names when jobs may run at the same time.
- Report results as tables: works / fails, job ids, nodes, exact error messages, versions.
